# Feature Specification: Build a Process from a Spreadsheet

**Feature Branch**: `claude/process-mapping-raci-tool-v1i9lb`

**Created**: 2026-09-19

**Status**: Draft

**Input**: User description: "create a file for me to download, add my inputs and upload it again and build the whole process automatically"

## Context

Every process in this product is built by hand: create it, add each step on the Process
Map, assign roles, draw the connections, then work through the RACI grid and the Authority
Matrix task by task. For a 22-step process that is a long sitting at a keyboard.

Consultants already gather this material in a spreadsheet during client workshops — the
steps, who does what, the approval limits. Today that spreadsheet is re-keyed into the app
a field at a time. This feature makes the spreadsheet the input.

The workbook is generated by the product rather than written by hand, so its columns always
match what the importer expects and a consultant never has to guess a header.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Build a process from a filled-in workbook (Priority: P1)

A consultant downloads the template, fills it in during or after a workshop, uploads it,
and the process exists: its steps in order, in their lanes, connected, with the RACI grid
and the authority rules already populated.

**Why this priority**: This is the request. Everything else here exists to make it safe.

**Independent Test**: Download the template, fill in a multi-step process, upload it, and
confirm the process appears complete on the Process Map, the RACI Matrix and the Authority
Matrix without further typing.

**Acceptance Scenarios**:

1. **Given** a filled-in template, **When** an editor uploads it, **Then** a new process is
   created with every step from the file, in the order the file gives them.
2. **Given** the same file, **When** the import finishes, **Then** each step sits in the
   lane of the role the file names, and the connections the file lists are drawn.
3. **Given** a file carrying RACI letters, **When** the import finishes, **Then** the RACI
   Matrix shows those assignments without further editing.
4. **Given** a file carrying authority rules, **When** the import finishes, **Then** the
   Authority Matrix shows those rules, each with its figure, its direction and who carries
   it.
5. **Given** a file naming a role that already exists in the workspace, **When** the import
   finishes, **Then** that existing role is used and no duplicate is created.
6. **Given** a successful import, **When** the consultant opens the new process, **Then**
   it is indistinguishable from one built by hand.

---

### User Story 2 - See what will happen before anything is written (Priority: P1)

Before the import writes anything, the consultant is shown what it will create: how many
steps, which roles already exist and which are new, how many RACI assignments and authority
rules — and every problem found in the file, named by the sheet and row it is on.

**Why this priority**: Equal to User Story 1 and inseparable from it. A spreadsheet filled
in by hand will have typos. An import that writes half a process and then stops leaves
somebody unpicking it by hand, which is worse than not having the feature.

**Independent Test**: Upload a file with several deliberate mistakes and confirm nothing is
created and every mistake is reported with its location.

**Acceptance Scenarios**:

1. **Given** a valid file, **When** it is uploaded, **Then** the consultant sees a summary
   of what will be created and must confirm before anything is written.
2. **Given** a file with any error, **When** it is uploaded, **Then** nothing is created,
   and every error is listed with the sheet and row it came from.
3. **Given** a file naming a role that does not exist in the workspace, **When** it is
   uploaded, **Then** the summary says that role will be created, by name, before the
   consultant confirms.
4. **Given** a file the consultant decides against, **When** they decline, **Then** nothing
   is created and no trace of the upload remains.
5. **Given** an import that fails part way through for any reason, **When** it stops,
   **Then** no half-built process is left behind.

---

### User Story 3 - A template that explains itself (Priority: P2)

The consultant downloads a workbook that already says what each sheet is for, what each
column accepts, and shows a worked example they can overwrite.

**Why this priority**: Without it the first two stories still work, but only for someone
who has been shown the format once. A template that needs explaining is a template that
generates support questions.

**Independent Test**: Give the template to someone who has not seen it, and see whether
they can fill it in without asking what a column means.

**Acceptance Scenarios**:

1. **Given** the Processes page, **When** an editor downloads the template, **Then** they
   get a workbook with a sheet for each part of a process.
2. **Given** the template, **When** a consultant opens it, **Then** each sheet states what
   it is for and each column what it accepts.
3. **Given** a column that only accepts certain values, **When** a consultant fills that
   column in, **Then** the accepted values are stated in the template rather than having to
   be remembered.
4. **Given** the template, **When** a consultant looks at it, **Then** it contains a short
   worked example showing a small complete process.
5. **Given** the template as downloaded and never edited, **When** it is uploaded, **Then**
   the example imports successfully — so the round trip is known to work before a
   consultant invests a workshop in it.

---

### User Story 4 - Only editors, and only creating (Priority: P2)

Importing writes a great deal at once. A read-only user is offered no way to do it, and the
import can only create a new process — never overwrite one that exists.

**Why this priority**: The damage an import can do is larger than any other single action
in the product, which is what makes the boundary worth stating rather than assuming.

**Independent Test**: As a viewer, confirm no download or upload control appears and a
direct request is refused.

**Acceptance Scenarios**:

1. **Given** a read-only user, **When** they open the Processes page, **Then** they are
   shown neither the template download nor the upload control.
2. **Given** a read-only user, **When** they submit an import directly, **Then** it is
   refused.
3. **Given** a file naming a process whose name already exists in the workspace, **When**
   it is uploaded, **Then** the consultant is told, and the import creates a separate
   process rather than changing the existing one.
4. **Given** any import, **When** it completes, **Then** no process other than the new one
   has changed.

---

### Edge Cases

- **An empty template.** The template downloaded and uploaded with the example deleted and
  nothing put in its place must be reported as empty, not imported as a nameless process.
- **A file that is not the template.** Any other workbook, or a file that is not a workbook
  at all, must be refused with a message saying what was expected.
- **A template from an older release.** A workbook whose sheets no longer match must be
  refused by name rather than silently importing the columns that still line up.
- **A connection naming a step that is not in the file.** Reported against the row it is
  on, not accepted as a dangling connection.
- **Two steps with the same name.** A connection naming that step is ambiguous; the file
  must be refused rather than guessing which was meant.
- **A task with two Accountables**, or none. The RACI rule is already enforced everywhere
  else in the product and must be enforced here.
- **A money rule with no figure**, or a rule with nobody to carry it. Reported like any
  other incomplete rule.
- **A very large file.** A process far larger than anyone would build by hand must either
  import or be refused for being too large — never accepted and then left half-written.
- **The same file uploaded twice.** Produces two processes, not one merged one, and the
  consultant is told a process of that name already exists before the second is created.

## Requirements *(mandatory)*

### Functional Requirements

**The template (User Story 3)**

- **FR-001**: The system MUST offer editors a downloadable workbook template from the
  Processes page.
- **FR-002**: The template MUST be generated by the product, so that its structure always
  matches what the importer accepts.
- **FR-003**: The template MUST carry a sheet for each part of a process: the process
  itself, its steps, the connections between them, the RACI assignments, the authority
  rules, the KPIs and the external entities.
- **FR-004**: Each sheet MUST state what it is for, and each column what it accepts,
  including the permitted values where a column is restricted.
- **FR-005**: The template MUST contain a worked example of a small complete process.
- **FR-006**: The template as downloaded MUST import successfully without being edited.

**Importing (User Story 1)**

- **FR-007**: Editors MUST be able to upload a filled-in template and have a new process
  created from it.
- **FR-008**: The import MUST create the process, its steps in the given order and type,
  each in the lane of its named role, with the connections the file lists.
- **FR-009**: The import MUST create the RACI assignments the file gives.
- **FR-010**: The import MUST create the authority rules the file gives, each with its
  measure, figure, direction, consequence and who carries it.
- **FR-011**: The import MUST create the process's own documentation — purpose, scope,
  KPIs and external entities — where the file provides it.
- **FR-012**: The import MUST match a role or person named in the file to an existing one
  of that name in the workspace rather than creating a duplicate.
- **FR-013**: The import MUST create a role or person the workspace does not have, and MUST
  have said so in the summary first.
- **FR-014**: The process code MUST be generated by the system, as it is for a process
  created by hand. The template MUST NOT invite one.

**Safety (User Story 2)**

- **FR-015**: The system MUST show the consultant what the import will create, and get
  their confirmation, before writing anything.
- **FR-016**: The summary MUST state at least: the process name, the number of steps and
  connections, which roles and people already exist and which will be created, and the
  number of RACI assignments and authority rules.
- **FR-017**: Every problem found in the file MUST be reported with the sheet and row it
  came from.
- **FR-018**: A file with any error MUST NOT be imported, in whole or in part.
- **FR-019**: An import MUST either complete entirely or leave nothing behind. No
  half-built process may survive a failure at any point.
- **FR-020**: Declining at the summary MUST leave nothing behind.
- **FR-021**: The rules the importer enforces MUST be the same rules the product enforces
  everywhere else — one Accountable per task, a money rule carries a figure, a connection
  joins two steps that exist.
- **FR-022**: A file that is not this template MUST be refused with a message saying what
  was expected, rather than partially understood.

**Access and scope (User Story 4)**

- **FR-023**: Importing MUST require edit access, checked on the server regardless of what
  the page displayed.
- **FR-024**: A user without edit access MUST be shown neither the template download nor
  the upload control.
- **FR-025**: An import MUST only create a new process. It MUST NOT modify or replace an
  existing one.
- **FR-026**: An import MUST NOT change any process other than the one it creates.

### Key Entities

- **Template workbook**: What the product hands a consultant to fill in. Generated on
  demand; nothing is stored.
- **Parsed import**: What was read out of an uploaded file — the process, its steps,
  connections, assignments and rules — before anything is written. Exists only for the
  length of the request.
- **Import summary**: What will be created if the consultant confirms, including which
  roles and people are new. Shown, not stored.
- **Import problem**: One thing wrong with the file, carrying the sheet and row it came
  from and what is wrong in words a consultant can act on.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A consultant can turn a filled-in workbook into a complete process without
  typing anything into the app beyond confirming the summary.
- **SC-002**: A 22-step process with roles, connections, RACI and authority rules imports
  in one upload, where building it by hand takes a sitting of an hour or more.
- **SC-003**: A file with mistakes never creates anything, 100% of the time.
- **SC-004**: Every reported problem names the sheet and row it is on, so a consultant can
  go straight to it without hunting.
- **SC-005**: A process created by import is indistinguishable from one built by hand — it
  can be edited, exported and reported on identically.
- **SC-006**: A consultant who has not seen the template before can fill it in without
  asking what a column means.
- **SC-007**: No user without edit access can import, and none is shown a control for it.

## Assumptions

- **A spreadsheet, because that is what consultants already use.** The material arrives
  from workshops in spreadsheets; asking for any other format would mean re-keying, which
  is the thing this feature exists to remove.
- **One process per file.** A workbook describes one process. Importing several at once is
  a larger idea and is out of scope.
- **Names are the join.** Roles, people and steps are matched by the names written in the
  file, because a consultant filling in a spreadsheet has no access to the product's
  internal identifiers.
- **Creating only.** An import makes a new process. Updating an existing process from a
  file is a materially riskier thing — it implies deciding what to do about steps that
  have been edited since — and is deliberately not attempted.
- **The whole file or none of it.** Partial success is not offered even where it would be
  possible, because a half-built process is harder to deal with than a rejected file.
- **Validation reuses the product's own rules** rather than restating them, so an imported
  process cannot be in a state the app would refuse to let anyone create by hand.
- **The template carries its own example**, which doubles as the round-trip test: if the
  untouched template imports, the format and the importer agree.

## Out of Scope

- Updating or merging into an existing process from a file.
- Importing more than one process from a single file.
- Importing the org directory, the value chain or the phases — this is one process at a
  time.
- Matching a role by anything other than its name, including fuzzy matching or suggesting
  near-misses.
- Scheduled or automated imports, or importing from anywhere but an upload by hand.
- Exporting a process back into this same template format for round-tripping.
